# Замечания ревью проверки договора и её тестов

Дата: 22 октября 2026 года.

Статус: замечания зафиксированы, исправления пока не выполнены.
Приоритет P2 — обычная очередь исправления, P3 — улучшение удобства разработки.

## 1. P2: версия установленного mockgen не проверяется

**Место:** `Makefile`, цели `install-mockgen` и `$(MOCKGEN)`.

Генератор устанавливается только при отсутствии бинарного файла в `.tools`.
Изменение `MOCKGEN_VERSION` не приводит к обновлению уже установленного генератора.
В результате разработчики и CI могут генерировать mock разными версиями инструмента.

**Воспроизведение:** при существующем бинарнике команда
`make -n install-mockgen MOCKGEN_VERSION=v9.9.9` сообщает, что выполнять нечего.
Это проверка поведения Make, а не предложение устанавливать указанную версию.

**Ожидаемое исправление:** проверять установленную версию либо выполнять установку
закреплённой версии при вызове цели установки.

**Критерий готовности:** смена `MOCKGEN_VERSION` приводит к использованию новой
версии; генерация у разработчика и CI использует версию из Makefile.

## 2. P3: go generate зависит от переменной Makefile

**Место:** директивы `go:generate` в `internal/service/contract_checker.go`
и `internal/service/dependencies.go`.

Команды используют `$MOCKGEN`, который экспортируется Makefile. Запуск через
`make generate-mocks` работает. Прямой запуск `go generate ./internal/service`
или генерация из IDE без этой переменной не работают.

**Ожидаемое решение:** сделать директивы самостоятельными либо явно принять
и описать запуск исключительно через Make. Текущая зависимость от Make уже
описана в `docs/testing.md`, но удобство запуска из IDE остаётся ограниченным.

**Критерий готовности:** выбран и проверен поддерживаемый способ генерации;
инструкция не предполагает неявно настроенное окружение.

## 3. P2: некорректный ответ принимается за бизнес-отказ

**Место:** `internal/clients/contract/client.go`, метод `CheckOption`.

Ответ HTTP 200 с `{}` или `{"data":null}` может успешно декодироваться
в сгенерированные структуры. Отсутствующий `allowed` получает нулевое значение
`false`. Клиент возвращает бизнес-отказ без ошибки, и создание заявки отвечает
HTTP 403 вместо технической ошибки HTTP 500.

Проблема существовала до перехода на gomock. При планировании она была отмечена,
но в рамках выполненной работы исправление и отдельные тесты не добавлены.

**Ожидаемое исправление:** проверять обязательные данные успешного ответа.
Отсутствующий `data`, `data:null` и отсутствующий `allowed` должны отличаться
от корректного `allowed:false`. Одной проверки значения bool недостаточно.

**Критерии готовности:**

- Некорректные успешные ответы приводят к ошибке клиента, а не к бизнес-отказу.
- Корректный `allowed:false` с причиной сохраняет прежнее поведение.
- Через API нарушение контракта приводит к HTTP 500 без сохранения заявки и истории.

## 4. Неполное покрытие расширенного плана тестирования

Основные требования урока покрыты. Следующие проверки были включены
в расширенный план, но пока не реализованы.

### Отмена во время ожидания ретрая

Сейчас проверяется контекст, отменённый до отправки запроса. Нет отдельной проверки
отмены после первого HTTP 500, во время паузы перед повтором.

**Ожидание:** клиент возвращает ошибку, распознаваемую через
`errors.Is(err, context.Canceled)`; второй HTTP-запрос не отправляется.

### Более короткий дедлайн вызывающего кода

Нет отдельной проверки, что дедлайн родительского контекста ограничивает проверку
раньше внутренних лимитов клиента: 500 мс на попытку и 1,2 секунды на всю проверку.

**Ожидание:** клиент прекращает работу по родительскому дедлайну, возвращает ошибку,
распознаваемую как `context.DeadlineExceeded`, и не начинает повтор после истечения
дедлайна. Проверка времени должна учитывать допуск на выполнение в CI.

### Создание заявки после успешного ретрая

В HTTP-тестах клиента есть последовательность `500 → 200, allowed=true`.
В интеграционных API-тестах с PostgreSQL нет аналогичного сценария,
проверяющего конечное сохранение.

**Ожидание:** Contract Service получает ровно два запроса; ShareTrip возвращает
HTTP 200, сохраняет ровно одну заявку в статусе `draft` и одну запись истории.

## 5. Компромиссы реализации, не являющиеся ошибками

- Интерфейс `TransactionBeginner` позволяет проверить отсутствие `BEGIN`
  без запуска PostgreSQL.
- Mock полного `pgx.Tx` увеличивает объём сгенерированного кода, но сохраняет
  существующую транзакционную функцию без дополнительной системы обёрток.
- После успешного `Commit` транзакционная функция вызывает отложенный `Rollback`.
  Это безопасный вызов, возвращающий `pgx.ErrTxClosed`; тест учитывает его.
- Unit-тесты проверяют взаимодействия сервисного слоя, а интеграционные тесты
  с PostgreSQL — фактическое сохранение. Один набор не заменяет другой.
