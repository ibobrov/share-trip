# Producer события TripPublished

ShareTrip отправляет событие после успешной публикации поездки. Consumer реализован
в отдельном проекте `share-trip-notification`: он создаёт уведомление и защищается
от повторной обработки через `processed_events`.

## Последовательность

1. Отдельным SELECT без блокировки и явной транзакции читаются данные поездки.
2. Проверяется владелец и разрешение `trip_publication` через Contract Service.
3. В транзакции поездка повторно читается через SELECT FOR UPDATE, проверяются
   владелец и актуальный статус, сохраняются статус, история и запись outbox.
4. После успешного COMMIT producer отправляет TripPublished в Kafka и ждёт ACK.
5. После подтверждения API возвращает 201. Повторная публикация владельцем уже
   опубликованной поездки возвращает 200 без нового события и записи истории.

Диаграмма: [PlantUML](diagrams/publish-trip-events.puml).

Асинхронность здесь означает независимость от обработки уведомления.
Подтверждение Kafka ожидается в пользовательском запросе; `Async=true` не используется.

## Контракт события

Topic: `trip.events`. Ключ сообщения: строковый UUID поездки `trip_id`.
Hash-балансировщик направляет события с одинаковым ключом в одну partition
при неизменном количестве partitions.

```json
{
  "event_id": "78910abc-1234-4567-89ab-1234567890ab",
  "event_type": "TripPublished",
  "trip_id": "f9b711e3-8f45-4dc3-8cab-07623f5de6e5",
  "client_id": "a1b2c3d4-1111-4111-8111-123456789abc",
  "company_id": "company-acme",
  "occurred_at": "2026-10-22T20:00:00Z"
}
```

Идентификатор события совпадает с `outbox_event.id`. Компания и клиент берутся
из записи, прочитанной под блокировкой. Время события в UTC соответствует времени
перехода статуса и записи истории. В outbox сохраняются trip_id, client_id и company_id;
время и идентификатор находятся в отдельных столбцах. Внутреннее имя события outbox
остаётся `trip_published`, внешнее значение `event_type` — `TripPublished`.

## Настройки и запуск

```text
KAFKA_BROKERS=localhost:9092
KAFKA_TRIP_TOPIC=trip.events
```

`KAFKA_BROKERS` принимает список адресов через запятую. Для приложения внутри
той же Docker-сети используется `kafka:29092`.

```text
docker compose --env-file .env -f deploy/docker-compose.yml up -d --wait kafka kafka-init kafka-ui
make run
```

Сервис `kafka-init` идемпотентно создаёт topic `trip.events`: три partitions,
replication factor 1 для локального брокера. При другом `KAFKA_TRIP_TOPIC`
нужно отдельно создать соответствующий topic.

Kafka UI: http://localhost:8085. После успешной новой публикации сообщение
доступно в разделе Messages topic `trip.events`. Consumer group `notification-service`
появляется после запуска Notification Service; после обработки продвигается её offset.

Producer использует `acks=all`, отправку без ожидания набора batch и до трёх
попыток kafka-go в пределах контекста отправки. Отправка ограничена одной секундой
и более коротким дедлайном вызывающего кода. Лимит HTTP-обработчика публикации —
4 секунды: до 1,2 секунды на Contract Service, время на БД, до секунды на Kafka.
Создание и получение поездки сохраняют лимит 2 секунды.

При штатном завершении приложение прекращает приём запросов, даёт обработчикам
до 5 секунд на завершение и закрывает producer и его транспорт.

## Ограничение этого этапа

COMMIT PostgreSQL и запись в Kafka не являются одной атомарной операцией.
Если producer вернул ошибку, API отвечает 500, но поездка уже опубликована:
статус, история и outbox сохраняются. Ошибка или timeout также не доказывают,
что Kafka не записала сообщение: подтверждение могло не дойти.

Текущая запись outbox не означает гарантированную доставку. Фонового отправителя
и отметок доставки пока нет. После сбоя повторный запрос публикации возвращает
200 для уже опубликованной поездки и не выполняет повторную отправку.
Надёжная доставка из outbox относится к следующему этапу; получатель должен будет
учитывать возможные дубликаты по event_id.

## Тесты

- Service-тесты с gomock фиксируют порядок COMMIT → producer и запрещают отправку
  при отказе договора, ошибке домена, outbox или COMMIT.
- API-тесты с PostgreSQL проверяют совпадение event_id с outbox, компанию, клиента,
  отсутствие повторной отправки и видимость опубликованного статуса из другой
  операции чтения в момент вызова producer.
- Unit-тесты адаптера проверяют JSON, ключ сообщения и передачу ошибки.
- Опциональный тест ниже отправляет и читает сообщение в настоящей Kafka через
  отдельный временный topic, который удаляется после проверки. Потребитель
  используется только для проверки producer. Consumer приложения реализован отдельно
  в Notification Service.

PowerShell:

```powershell
$env:KAFKA_TEST_BROKERS = 'localhost:9092'
go test ./internal/events -run TestProducer_Kafka -count=1 -v
```

Без `KAFKA_TEST_BROKERS` реальный Kafka-тест пропускается. Остальные тесты адаптера
и unit-тесты сервиса работают без Kafka; интеграционным API-тестам нужен Docker
для PostgreSQL.
