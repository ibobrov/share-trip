# Правила разработки Go-микросервиса

Документ основан на коде share-trip и предназначен для работы в этом репозитории и переиспользования в похожих сервисах. Срез реализации: 15 октября 2026 года. Правила ниже применяй к новому и изменяемому коду; они не являются поручением переписать весь проект.

При переносе замени имя модуля, сервиса, сущности, события, роли, порты и namespace метрик. Не переноси предметные правила поездок в другой домен. Точные версии и доступные команды проверяй в `go.mod`, `Makefile` и Compose. Существующие ограничения перечислены отдельно в конце.

## 1. Стек

| Область | Принятое решение в share-trip |
| --- | --- |
| Язык | Go 1.26.0, Go Modules |
| HTTP | Fiber v2, govalidator v12 |
| БД | PostgreSQL 16, pgx v5 и pgxpool, явный SQL без ORM |
| Миграции | Goose v3, версионированные SQL-файлы |
| Идентификаторы | UUID, `github.com/google/uuid` |
| Конфигурация | Переменные окружения, godotenv для локального `.env` |
| Авторизация | Keycloak, middleware аутентификации и проверки ролей |
| Логи | `log/slog`, JSON, контекст запроса |
| Метрики и трассировка | Prometheus, OpenTelemetry, OTLP HTTP, Collector, Jaeger |
| Сбор и просмотр логов | Alloy, Loki, Grafana |
| Тесты | `testing`, testify, Testcontainers с PostgreSQL |
| Инструменты | Make, golangci-lint v2, Docker Compose v2 |

Используй имеющиеся библиотеки. Добавляй зависимость, фреймворк или инфраструктурный компонент только при конкретной потребности задачи, объясняя выбор. Не обновляй версии попутно с несвязанным исправлением.

## 2. Архитектура и границы слоёв

Основной поток: `HTTP → middleware → api → service → domain → repository → PostgreSQL`.

Это слоистая архитектура с ручной сборкой зависимостей. В текущем проекте `domain` зависит от репозиториев, сущностей хранения и `pgx.Tx`; не называй её строгой Clean Architecture. Выделение независимого домена и портов — отдельная архитектурная задача.

```text
cmd/<service>/main.go       # сборка зависимостей, запуск и жизненный цикл
internal/api/              # маршруты, HTTP DTO, валидация формы, ответы
internal/service/          # координация сценариев, границы транзакций
internal/domain/           # бизнес-инварианты, права на сущность, переходы
internal/repository/       # SQL, подключение к БД, репозитории
internal/repository/entity/ # структуры хранения
internal/config/           # чтение и проверка конфигурации
internal/app/              # инфраструктурная сборка, настройка логгера
internal/observability/    # логи, метрики, трассы, существующие middleware
internal/api_test/         # интеграционные HTTP/БД-тесты
migrations/                # SQL-миграции Goose
deploy/                    # Compose и конфигурации инфраструктуры
docs/                      # бизнес-правила, сценарии и архитектура
```

- `cmd` создаёт пул, репозитории, use cases, сервисы и HTTP-сервер через конструкторы. Бизнес-логика здесь запрещена.
- `api` разбирает вход, получает identity из доверенного контекста, преобразует DTO и вызывает сервис. Не размещай SQL и управление транзакциями в обработчиках.
- `service` задаёт одну прикладную операцию, её транзакцию и последовательность use cases.
- `domain` проверяет бизнес-условия, владельца и допустимость перехода состояния. Проверка роли в middleware не заменяет проверку доступа к конкретной сущности.
- `repository` выполняет SQL и возвращает данные или ошибки. Не выбирает HTTP-коды и не фиксирует транзакцию прикладного сценария.
- Разделяй HTTP DTO, DTO сценария и структуры хранения; преобразуй их явно. Не возвращай сущность БД как публичный контракт по умолчанию.
- Сохраняй текущую модель зависимостей в локальных изменениях. Вводи небольшие интерфейсы на стороне потребителя, когда нужна конкретная подмена реализации; не создавай универсальные репозитории и DI-фреймворки без необходимости.
- Сервис владеет своей схемой. Межсервисное взаимодействие оформляй через API или события, без прямой записи в таблицы другого сервиса.

## 3. Написание кода и обработка ошибок

- Следуй `gofmt`, существующему расположению файлов по операциям и `.golangci.yml`. Новые Go-имена пиши с обычными сокращениями `ID`, `HTTP`, `URL`; не переименовывай весь старый код ради стиля.
- Передавай `context.Context` первым аргументом через все слои, запросы БД и внешние вызовы. Не заменяй контекст запроса на `context.Background()` в середине операции.
- Зависимости передавай через конструкторы. Не добавляй глобальное изменяемое состояние приложения.
- Делай функции небольшими, используй ранний возврат ошибок. Комментарии должны объяснять инвариант или причину решения.
- Оборачивай ошибки через `fmt.Errorf("operation: %w", err)`, классифицируй через `errors.Is`/`errors.As`, а не сравнение текста.
- Переводи `pgx.ErrNoRows` в предметную ошибку там, где известен смысл отсутствия данных. Проверяй ошибки `Scan`, `Exec`, `Commit`, закрытия ресурсов и `rows.Err()` после обхода результатов.
- Не используй `panic` и `log.Fatal` для штатных ошибок внутри библиотечных слоёв. Завершение процесса контролирует точка входа с учётом очистки ресурсов.
- Для нового API явно определяй JSON-контракт и HTTP-коды: 400 для некорректного запроса, 401/403 для доступа, 404 для отсутствия, 409 для конфликта, 500 для неожиданной ошибки. Уточняй семантику в контракте конкретного сценария.
- Не меняй существующие HTTP-коды share-trip и формат `{data, errors}` незаметно для клиентов. Изменение контракта должно быть частью задачи и отражаться в тестах и документации.
- Не выдавай клиенту SQL, DSN, токены и внутренние детали ошибки. Внутреннюю причину сохраняй в логах, внешнее сообщение делай безопасным.
- Для времени хранения используй `time.Time`, UTC и PostgreSQL `TIMESTAMPTZ`; правила сравнения времени задавай явно.

## 4. PostgreSQL и репозитории

- Используй один пул на процесс; создавай и проверяй соединение при старте, закрывай при остановке. Ограничения пула и таймауты выбирай с учётом числа экземпляров сервиса.
- SQL держи в репозиториях. Значения передавай параметрами `$1`, `$2`, …; не вставляй пользовательский ввод в SQL через конкатенацию. Динамические имена столбцов и сортировки выбирай из разрешённого набора.
- Перечисляй столбцы в `SELECT`/`INSERT`; порядок `Scan` должен соответствовать запросу. Проверяй `RowsAffected` там, где отсутствие изменения влияет на результат операции.
- Закрепляй инварианты ограничениями `NOT NULL`, `CHECK`, `UNIQUE`, внешними ключами. Доменная проверка даёт понятную ошибку, ограничение БД защищает данные при конкурентных запросах.
- Добавляй индексы под реальные фильтры, соединения и сортировки. Для существенных изменений запросов проверяй план на подходящих данных.
- Используй UUID для идентификаторов, JSONB — для структурированного payload событий. Не скрывай в JSONB данные, которым нужны обычные связи и ограничения.
- Не копируй междоменные внешние ключи и `ON DELETE CASCADE` автоматически: удаление истории и политика хранения требуют предметного решения.

## 5. Транзакции, конкуренция и outbox

- Границу транзакции определяет `service`. Используй общий helper из `internal/service/transaction.go`: begin → сценарий → commit, с отложенным rollback.
- Передавай один и тот же `pgx.Tx` во все связанные use cases и репозитории. Запись сущности, её истории и outbox должна фиксироваться целиком либо полностью откатываться.
- Не открывай независимую транзакцию и не используй пул напрямую для части атомарной операции. Не вызывай `Commit`/`Rollback` в репозитории.
- Считай операцию успешной только после успешного commit. Ошибку commit возвращай вызывающему коду. Не повторяй операцию вслепую, если результат фиксации неизвестен.
- Rollback после успешного commit может вернуть `pgx.ErrTxClosed`; это ожидаемо. Остальные ошибки очистки учитывай, сохраняя исходную ошибку операции. При доработке helper учти отмену исходного контекста: очистка должна иметь отдельный ограниченный по времени контекст.
- Для изменения по текущему состоянию используй блокировку строки (`SELECT … FOR UPDATE`) либо условный атомарный `UPDATE` с проверкой результата. Проверку состояния и изменение выполняй в одной транзакции.
- При блокировке нескольких строк соблюдай единый порядок. Держи транзакции короткими, не выполняй сетевые запросы или длительные вычисления под блокировкой.
- Явно определяй семантику повторного запроса. В share-trip повторная публикация владельцем успешна и не создаёт повторную историю или событие; проверка владельца предшествует этому раннему возврату.
- Внешнее событие сохраняй в outbox в транзакции бизнес-изменения; отправляй отдельным обработчиком после commit. Сохранение outbox не означает доставку сообщения.
- При реализации доставки учти повторные попытки и дубли: стабильный ID события, учёт обработки и идемпотентный потребитель. Не обещай exactly-once без соответствующего протокола.
- Изоляцию транзакций и повторы после deadlock/serialization failure меняй осознанно; повторять допустимо всю безопасную операцию с ограниченным числом попыток.

## 6. Миграции

- Любое изменение схемы оформляй новой SQL-миграцией Goose в `migrations/<timestamp>_<action>.sql`. Уже применённые совместно используемые миграции не редактируй.
- Создавай файл командой `make migrate-create name=create_entity`. Сохраняй уникальный timestamp и порядок зависимостей: типы → таблицы → зависимые объекты.
- Пиши секции `-- +goose Up` и `-- +goose Down`. Для многооператорных SQL-блоков используй `StatementBegin`/`StatementEnd` по необходимости. Down удаляет зависимости в обратном порядке.
- Если изменение данных необратимо, укажи это явно; не имитируй безопасный rollback. Откат схемы не восстанавливает удалённые данные.
- По умолчанию сохраняй транзакционное выполнение миграции. Операции, несовместимые с транзакцией, выноси отдельно с явной конфигурацией Goose и планом восстановления после частичного выполнения.
- Для изменения существующих данных продумывай совместимость старой и новой версии приложения: добавление → заполнение → переключение → удаление устаревшего. Учитывай блокировки и объём backfill.
- Применение миграций — отдельный этап, а не побочный эффект HTTP-запроса или старта каждого экземпляра приложения.
- Проверяй Up на чистой БД и обновление с предыдущей схемы. Если Down поддерживается, проверяй цикл Up → Down → Up только на одноразовой БД.
- Перед командами миграции проверяй целевое окружение. Не запускай откаты и разрушительные изменения на рабочей БД как способ проверки.

## 7. Makefile и рабочий цикл

Makefile — единая точка входа для повторяемых операций. Запускай команды из корня репозитория.

| Команда | Назначение |
| --- | --- |
| `make help` | Список команд |
| `make deps` | Зависимости и локальные CLI-инструменты |
| `make tidy` | Осмысленное обновление go.mod/go.sum при изменении зависимостей |
| `make fmt` | Форматирование Go-кода |
| `make lint` | Проверки `.golangci.yml` |
| `make test` | Все тесты; интеграционным тестам нужен Docker |
| `make build` / `make run` | Сборка в `bin/` / локальный запуск |
| `make up` / `make down` | Запуск с ожиданием готовности / остановка Compose |
| `make migrate-status` | Состояние миграций целевой БД |
| `make migrate-up` / `make migrate-down` | Применение / откат последней миграции |
| `make migrate-create name=create_entity` | Создание SQL-миграции |
| `make coverage` / `make coverage-html` | Покрытие и отчёт в `.reports/` |

- Для первого запуска настрой локальное окружение, выполни `make deps`, `make up`, `make migrate-status`, `make migrate-up`, затем `make run`. Keycloak запускается и настраивается отдельно.
- Новые команды объявляй в `.PHONY` и описывай в `help`. Сохраняй поддержку Windows (`.exe`, создание каталогов) и Unix-подобных окружений.
- Устанавливай инструменты в `.tools/` с фиксированными версиями. Учитывай совместимость Go, линтера и Goose CLI; версия CLI и библиотека в `go.mod` задаются отдельно.
- Для изменения Go-кода выполняй `make fmt`, `make lint`, `make build` и подходящие тесты; перед завершением функционального изменения — `make test` при доступном Docker. Не подменяй интеграционные проверки одной компиляцией.
- Для правки только документации достаточно проверки содержимого, ссылок и diff. Не сообщай об успешных тестах, если они не запускались; указывай причину пропуска или сбоя.

## 8. Docker и конфигурация

- Локальная инфраструктура описана в `deploy/docker-compose.yml`. Используй команду из Makefile: `docker compose --env-file .env -f deploy/docker-compose.yml`.
- В текущем Compose находятся PostgreSQL и наблюдаемость; приложение запускается через `make run`. Dockerfile приложения пока отсутствует.
- Согласуй `DB_*` приложения, `POSTGRES_*` контейнера и `GOOSE_DRIVER`/`GOOSE_DBSTRING` мигратора. С хоста используй опубликованный порт; между контейнерами — DNS-имя сервиса и внутренний порт.
- Храни секреты в окружении или предназначенном для этого хранилище. Для новых параметров поддерживай несекретный `.env.example`; не коммить `.env` и не выводи его содержимое в отчёты.
- Проверяй обязательные параметры при старте. Локальные fallback-пароли и `sslmode=disable` не должны становиться настройками эксплуатации по умолчанию.
- Для новых контейнеров фиксируй версию образа или digest, задавай healthcheck и корректный порядок зависимостей. Простой `depends_on` не гарантирует готовность БД; используй `service_healthy`, для init-задач — `service_completed_successfully`.
- Постоянные данные размещай в именованных volumes, конфигурации монтируй read-only. Не используй `down -v` для обычной остановки: он удаляет данные volumes.
- Не добавляй фиксированные `container_name` без необходимости: они мешают параллельным окружениям. Выделяй отдельные порты и Compose project name для нового сервиса.
- Если задача требует упаковки приложения, создай multi-stage Dockerfile: сборка подходящей версией Go, минимальный runtime с нужными сертификатами, непривилегированный пользователь, только необходимые артефакты. Исключи секреты и локальные файлы через `.dockerignore`.
- Для нового фонового процесса или контейнеризованного сервиса реализуй остановку по сигналу: прекращение приёма запросов, завершение работников, закрытие пула и flush телеметрии с таймаутом.
- После изменения Compose проверяй конфигурацию без публикации раскрытых секретов, затем готовность затронутых сервисов, если окружение позволяет запуск.

## 9. Наблюдаемость и тестирование

- Передавай request ID и логгер через контекст. Используй структурированные поля `layer`, `operation`, идентификатор сущности; не логируй токены, пароли и полные чувствительные payload.
- Сохраняй связность трасс между слоями и закрывай spans. Метрики должны учитывать ошибки и фактический итог транзакции.
- В labels метрик используй шаблоны маршрутов и ограниченные наборы результатов. Не добавляй UUID, произвольные URL или тексты ошибок.
- Согласуй HTTP-порт, scrape target, доступ к `/metrics`, OTLP endpoint и путь файловых логов. Технические маршруты должны иметь явно выбранную политику доступа.
- SQL, ограничения и транзакции проверяй на настоящем PostgreSQL через Testcontainers и те же Goose-миграции. Не заменяй эти проверки SQLite или исключительно моками.
- Проверяй успешный результат, входную валидацию, отсутствие сущности, чужого владельца, запрещённый переход, повторный запрос и состояние БД после ответа.
- Для нескольких связанных записей добавляй проверку полного rollback при ошибке позднего шага. Для конкурентного изменения проверяй гонку запросов, итоговое состояние и отсутствие лишних истории/событий.
- Изолируй тестовые данные UUID и очищай только свои записи. Используй `t.Parallel()` для независимых случаев; не меняй общую схему и глобальные данные одновременно с параллельными тестами.
- Изменения сборки зависимостей отражай и в `main`, и в тестовом приложении. Изменения авторизации проверяй отдельно: тестовый middleware не доказывает работу реального Keycloak.

## 10. Известные особенности исходного проекта

Это факты анализа, а не рекомендуемые шаблоны для нового сервиса:

- Ошибки валидации и `ErrDomain` сейчас могут возвращаться с HTTP 200; ошибки middleware не всегда используют общую оболочку ответа. Внутренняя ошибка может попадать клиенту через `err.Error()`.
- Keycloak middleware обменивает `X-Refresh-Token` на access token и декодирует полученные claims. Это не готовый валидатор произвольного входящего Bearer JWT.
- Outbox сохраняется атомарно, но отправщик, брокер, отметки доставки и retry пока не реализованы.
- HTTP graceful shutdown пока отсутствует. Rollback в helper использует исходный контекст запроса.
- Prometheus настроен на порт приложения 4000, fallback приложения — 8080; глобальная аутентификация затрагивает `/metrics`, а scrape не передаёт refresh token.
- Некоторые образы Compose используют `latest`. Не считай существующий Compose воспроизводимой production-конфигурацией.
- Goose CLI закреплён в Makefile на v3.26.0, библиотека в go.mod — v3.28.0. Учитывай различие при проверке миграций.
- Описанные в бизнес-документации сценарии могут ещё отсутствовать в коде. Не выдавай запланированное поведение за реализованное.

## 11. Порядок работы над задачей

1. Прочитай затронутый код, тесты и предметные документы. Проверь рабочий diff и сохрани чужие изменения.
2. Определи контракт операции, бизнес-инварианты, доступ, границы транзакции и необходимость миграции.
3. Внеси минимальное связное изменение по слоям; обнови сборку зависимостей, конфигурацию и документацию по необходимости.
4. Выполни проверки по характеру изменения. Отдельно проверь атомарность и конкуренцию, если они затронуты.
5. Проверь итоговый diff на случайные изменения, секреты и локальные артефакты. В отчёте укажи результат, выполненные проверки и оставшиеся ограничения.
